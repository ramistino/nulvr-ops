Fresh offline Python jsonschema Draft 2020-12 validation: **7/7 expected cases**: source example valid; invalid commit rejected; extra field rejected; missing work ID rejected; alternate declared track valid. Two trust-negative probes demonstrate a **semantic gap**: a handoff with `status:VERIFIED` or `status:RELEASED` and `evidence:[]` currently passes the v1 JSON Schema. This does not imply C2 has issued such a verdict—it means this structural schema cannot serve as proof of authorization or verification.

**Disposition:** v1 is adequate as a *format-only, untrusted work-handoff* contract, but **must not be treated as an authority/verdict validator**. In particular, an agent or script must not promote handoff status text to trusted PROVE `VERIFIED`, protected ledger, deployment or release action.

## Proposed small compatibility-safe v1.1 fix

Publish a new schema ID/path `ops/handoff-v1.1.schema.json` rather than silently mutate v1.0. For *untrusted handoffs*, permit only `PROPOSED`, `ACTIVE`, `BLOCKED`, `OBSERVED`, `UNVERIFIABLE`, `CHECK_ERROR`. Exclude `VERIFIED`, `REFUTED`, `RELEASED`, `ASSERTION_PASS`, `ASSERTION_FAIL` from handoff status: they belong to separate signed/rechecked evidence/decision records, not author-provided handoff prose. Require `authority_required` explicitly so the next gate is never an omitted implicit permission.

The current C2 example already has `authority_required:PROVE` and `status:PROPOSED`, so it remains valid under the narrowed v1.1 schema. Keep v1.0 as historical format-only data. Updating a schema alone is not a trusted runtime verifier; no permission changes, Actions workflow, deployment, main merge or spending follow.

**Next acceptance:** BUILD stages v1.1 on a separate branch; PROVE independently re-fetches the exact schema and re-runs valid/invalid fixtures. Adopt the v1.1 *contract* in the company branch after review, but no automated governance CI until separately approved.
